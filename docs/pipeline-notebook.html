DROP data, html, screenshot.data      raw banner text / full page HTML / base64 images — not queryable signals
DROP ssl.chain                     raw PEM certs, ~500B+/row where present, cert subject not pre-parsed anyway

KEEP hostnames, domains             entity resolution backbone
KEEP location, org, isp, asn
KEEP os, product, devicetype, tags, cpe23
KEEP vulns                         CVE map: cvss, epss, summary
KEEP ssl.jarm, http.status/server/title, _shodan.module

Issue found while running the first ingestion attempt

data quality issue #1 — oversized record

One record is ~25MB, bigger than DuckDB's default 16MB object-size limit

First run of pipeline/silver/hosts.py failed outright:

_duckdb.InvalidInputException: "maximum_object_size" of 16777216 bytes
exceeded while reading file (>25323446 bytes).

Root cause: a rare record (likely with a large embedded screenshot/HTML blob) exceeds the parser's default per-object cap.

Fix logic: raise maximum_object_size to 128MB in the read_json() call — generous headroom without loading the whole 84.6GB into memory at once (DuckDB still streams row by row).

Fixed: read_json(..., maximum_object_size = 134217728)

Result

Same row count as input — this stage only removes unused columns and compresses, it drops zero rows (verified by a null-rate/row-count sanity check).

Entity Resolution: host rows → companies

Silver Hosts is at (ip, port, timestamp) grain — one row per exposed service. A sales rep thinks in companies. Look at what the identifying fields actually contain before writing the merge logic:

In [3]:
SELECT org, count(*) FROM hosts GROUP BY 1 ORDER BY 2 DESC LIMIT 5
Out[3]:
Google LLC              2,020,662
Incapsula Inc           1,737,105
Cloudflare, Inc.          302,320
Amazon.com, Inc.          278,775
Aliyun Computing Co.      235,920

The top org values are all hyperscalers/CDNs — the tenant running on that IP, not the company we'd sell to. org alone can't be the join key. Decision: a 3-tier resolver — domain (from hostnames/domains, filtered against a hyperscaler/CDN/brand denylist) → org (fallback, filtered against the same + generic-ISP keywords) → unresolved (counted, not discarded).

DROP-ish 6,952,490 rows (78.0%) → unresolved  hyperscaler/CDN tenant IPs, can't attribute to a real business
RESOLVE 1,163,517 rows (13.1%) → org-tier
RESOLVE   798,686 rows ( 9.0%) → domain-tier
                8,914,693 total   ✓ sums to Stage 1's row count

Issue #2 — NULL propagation silently mis-buckets rows

data quality issue #2

Rows with a missing ISP fell into "unresolved" even when the org was a real company

First resolution run, sampling what landed in the unresolved bucket:

('ACEVILLE PTE.LTD.', None, 84972)   org, isp, count — isp is NULL

Root cause: the hyperscaler-check was lower(isp) LIKE '%google%' OR .... In SQL, NULL LIKE anything evaluates to NULL, not false — and NULL poisons the surrounding OR/NOT chain, so any row with a missing isp silently fell through to unresolved regardless of what org said.

Fix logic: wrap in COALESCE(lower(isp), '') so a missing value compares as empty string (definitively false) instead of unknown.

Fixed: unresolved dropped from 80.0% → 78.0% of rows; ACEVILLE now correctly lands in org-tier.

Issue #3 — punctuation splits one company into two keys

data quality issue #3

"Meteverse Limited" and "Meteverse Limited." were treated as different companies

('meteverse limited',  78,292)
('meteverse limited.', 62,702)   ← same company, trailing period only

Root cause: org-tier key was lower(trim(org)) — trims whitespace but not trailing punctuation.

Fix logic: regexp_replace(lower(trim(org)), '[\s.,]+$', '') — strip trailing periods/commas/whitespace before grouping.

Fixed: 
('meteverse limited', 140,994)   78,292 + 62,702, merged — verified equal

Issue #4 — a handful of "companies" are actually proxy networks

data quality issue #4

No single business owns 130,000 IPs

Top org-tier companies by host count included entries no real SMB could produce: ACEVILLE PTE.LTD. (130,066 hosts, 3 ASNs), Internet Rimon (92,769), Meteverse Limited (140,994) — proxy/hosting networks whose names don't happen to contain any denylist keyword.

Fix logic: flag (not drop) org-tier rows with host_count ≥ 500 as likely_infra_or_proxy — keeps the row for transparency, lets scoring discount it.

Result: 237 flagged companies (0.13% of resolved companies) hold 780,194 hosts — ~40% of all resolved host volume. Confirms these would have dominated any un-flagged volume-based score.

Issue #5 — row-count mismatch surfaced a join bug

data quality issue #5

Security Signals (next stage) had fewer rows than Silver Companies — 186,435 vs 187,007

Two compounding bugs, found by insisting the two tables' counts match exactly rather than accepting "close enough":

(a) Key collision: joining/grouping on company_key alone let an unrelated domain-tier and org-tier key collide if the strings happened to match. Fix: use the composite (company_key, resolution_tier) everywhere downstream.

(b) NULL join: ip_str is NULL on 1.2% of rows; NULL = NULL is unknown in SQL, so those rows never joined. Fix: join on (ip_str, port, ts) with IS NOT DISTINCT FROM for ip_str (NULL-safe equality).

Fixed: counts now match exactly, 187,106 = 187,106.

Issue #6 — counts silently became NULL / floats

data quality issue #6

"hurricane electric" showed eol_count = None instead of 0, and numbers rendered as floats

('hurricane electric', 'org', 246720.0, 10.0, 0.99999, True, None, None, 0.0)
                              cve_count as float ^        eol_count/self_signed_count NULL ^

Root cause, part 1 (NULL): is_eol_product::INT is itself NULL whenever the host's tags field is NULL (33.1% of rows) — list_contains(NULL, 'x') returns NULL, not false. SUM() of an all-NULL group returns NULL, not 0.

Root cause, part 2 (float): Parquet has no native 128-bit integer type. DuckDB's SUM() computes internally as HUGEINT, then silently downcasts to DOUBLE on write — which is why the customer-facing why[] text later read "16.0 host(s)" instead of "16".

Fix logic: CAST(coalesce(sum(is_eol_product::INT), 0) AS BIGINT) on every count aggregate — explicit zero-default and explicit integer type.

Fixed: counts are clean integers; "16 host(s)" not "16.0 host(s)".

Gold Scoring — fit × urgency → band

Combine reachability/size/vertical/geography (fit) with CVE/EPSS/EOL/self-signed/risky-ports (urgency) into one contact_score, banded contact / review / skip / exclude.

SELECT company_key, primary_org, band, contact_score, why
FROM accounts ORDER BY contact_score DESC LIMIT 3

Issue #7 — a "contact"-band prospect that wasn't real

data quality issue #7

amazon.com scored 93 and landed in the contact band

company_key = amazon.com    primary_org = NTT America, Inc.   c2_count = 1

Root cause: the resolved org wasn't Amazon at all — NTT America, Inc., and the host was flagged c2 (possible command-and-control). Almost certainly a spoofed reverse-DNS PTR record impersonating the brand: PTR records are set by whoever owns the IP block, not by the real domain's registrant, so they're trivially faked. Our resolver trusted the domain string at face value.

Fix logic: added a BRAND_DOMAINS denylist (amazon.com, google.com, microsoft.com, apple.com...) — at that scale, a resolved domain is never a genuine SMB lead, it's either infra we should've already caught, or impersonation.

data quality issue #8

'localhost.' aggregated 2,375 unrelated hosts into one fake company

company_key = localhost.   host_count = 2375
sample_hostnames = [undefined.hostname.localhost, a248.e.akamai.net, localhost]

Root cause: generic placeholder hostnames from misconfigured devices across many unrelated networks all reduce to the same reserved domain string.

Fix logic: added a RESERVED_PLACEHOLDER_DOMAINS denylist (localhost, localdomain, invalid, example.com/net/org).

Fixed: re-ran the full pipeline — neither amazon.com nor localhost. appear in the output anymore.
