Ingestion

1 issue
01A record bigger than the parser's default limit›
Found

The first full run of the ingestion script failed outright: "maximum_object_size" of 16777216 bytes exceeded.

Root cause

One record (likely a large embedded screenshot/HTML blob) is ~25MB — DuckDB's JSON parser defaults to a 16MB per-object cap.

Fix

Raised maximum_object_size to 128MB in the ingestion call.

Verified

Full 84.6GB scan completes; 8,914,693 rows written, matching the raw line count exactly.

Entity Resolution

5 issues
02NULL silently mis-buckets rows›
Found

QA-sampling the "unresolved" bucket surfaced a real company sitting where only cloud/CDN tenant IPs should be:

('ACEVILLE PTE.LTD.', None, 84972)
Root cause

The hyperscaler check was lower(isp) LIKE '%google%' OR .... In SQL, NULL LIKE anything is NULL, not false — it poisons the surrounding OR/NOT chain. Any row with a missing isp (8.6% of rows) fell through to unresolved regardless of what org said.

Fix

Wrapped in COALESCE(lower(isp), '') so a missing value compares as empty string, not unknown.

Verified

Unresolved dropped from 80.0% to 78.0% of rows; ACEVILLE now correctly resolves.

03Punctuation splits one company into two›
Found

Two "different" top companies, same business:

('meteverse limited', 78,292) ('meteverse limited.', 62,702)
Root cause

The key was lower(trim(org)) — trims whitespace, not trailing punctuation.

Fix

regexp_replace(lower(trim(org)), '[\s.,]+$', '')

Verified

Merged into one row, 140,994 hosts — exactly 78,292 + 62,702.

04Proxy/hosting networks mistaken for one company›
Found

Top "companies" no real business could be: ACEVILLE PTE.LTD. (130,066 hosts, 3 ASNs), Internet Rimon (92,769 hosts).

Root cause

Proxy/hosting networks whose names don't contain any denylist keyword — a keyword denylist is incomplete by construction.

Fix

Flagged (not dropped) rows with host_count ≥ 500 as likely_infra_or_proxy — kept for transparency, discounted in scoring.

Verified

237 flagged companies (0.13% of resolved companies) held 780,194 hosts — ~40% of all resolved volume. Would have dominated any un-flagged signal.

11ISPs' own customers mistaken for the ISP›
Found

comcast.net (2,803 hosts), spectrum.com (12,821 hosts) sitting in the sample, some scoring a perfect 100. swisscom.ch (437 hosts) had zero other reason to be excluded — its hostnames read:

179.202.41.212.static.wline.lns.sme.cust.swisscom.ch

Swisscom's own naming convention for its broadband customers' static IPs.

Root cause

Issue #4's likely_infra_or_proxy flag only applied to org-tier companies; domain-tier had no equivalent check. The dynamic-PTR detector also only caught dash-separated IPs (77-163-107-27.fixed...), missing this dot-separated pattern entirely.

Fix

Extended the infra flag to domain-tier (host_count ≥ 500, any tier). Generalized the PTR detector to also match dotted-IP prefixes and explicit markers (static, dynamic, cust, pool, dsl, dial, dhcp).

12A trailing dot defeated the domain-plausibility check›
Found

'vds.' (81 hosts, a hosting provider's internal VPS-naming suffix, not a real domain) still appeared after adding a "must contain a dot" check.

Root cause

"vds." technically contains a dot — at the very end. The naive LIKE '%.%' check didn't distinguish a real SLD.TLD structure from a bare label with a stray trailing period.

Fix

regexp_replace(lower(d), '\.$', '') to strip a trailing dot before checking for a real remaining one.

Verified

Both swisscom.ch and vds. gone from results; final count 189,257 resolved companies.

Pipeline Correctness

2 issues
05A row-count mismatch traced to two compounding bugs›
Found

Security Signals produced 186,435 rows against Silver Companies' 187,007. Insisting on an exact match, not "close enough," surfaced two separate bugs.

Root cause (a)

Key collision: joining on company_key alone let an unrelated domain-tier and org-tier key collide if the strings happened to match.

Root cause (b)

NULL-unsafe join: ip_str is NULL on 1.2% of rows; SQL's NULL = NULL is unknown, not true — those rows never joined, and any company whose only hosts had a NULL ip_str vanished entirely.

Fix

(a) Composite key (company_key, resolution_tier) everywhere downstream. (b) Join on (ip_str, port, ts) using IS NOT DISTINCT FROM for NULL-safe equality.

Verified

Counts now match exactly: 187,007 = 187,007.

06Parquet has no 128-bit integer — numbers became floats›
Found

Customer-facing text read "16.0 host(s) running end-of-life software" instead of "16"; a sanity query showed counts that should never be NULL:

('hurricane electric', ..., None, None, 0.0)
Root cause (NULL)

is_eol_product::INT is itself NULL whenever a host's tags field is NULL (33.1% of rows) — list_contains(NULL, 'x') returns NULL, and SUM() of an all-NULL group returns NULL, not 0.

Root cause (float)

DuckDB's SUM() computes internally as HUGEINT (128-bit). Parquet has no native 128-bit integer type, so it silently downcasts to DOUBLE on write.

Fix

CAST(coalesce(sum(...), 0) AS BIGINT) on every count aggregate.

Verified

Clean integers throughout — "16 host(s)", not "16.0 host(s)".

Gold Layer & Denylists

4 issues
07A "contact"-band prospect that was a spoofed brand›
Found

amazon.com sitting in the contact band, score 93.

Root cause

Its resolved org was NTT America, Inc., not Amazon, and the host was flagged c2 (possible command-and-control) — almost certainly a spoofed reverse-DNS PTR impersonating the brand. PTR records are controlled by the IP block's owner, not the real domain's registrant, so they're trivially fakeable.

Fix

Added a brand-domain denylist (amazon.com, google.com, microsoft.com...) — at that scale, a resolved domain is never a genuine lead, it's infrastructure already caught elsewhere, or impersonation.

08A placeholder hostname aggregated thousands of unrelated hosts›
Found

'localhost.' had aggregated 2,375 hosts into one fake company, sample hostnames including undefined.hostname.localhost.

Root cause

Generic placeholder hostnames from misconfigured devices across many unrelated networks all reduce to the same reserved domain string.

Fix

Added a reserved/placeholder domain denylist (localhost, localdomain, invalid, example.com/net/org).

09A reserved DNS zone treated as a company›
Found

37.in-addr.arpa sitting in the contact band with a perfect score.

Root cause

.in-addr.arpa is an IANA-reserved reverse-DNS zone, not a real registrable domain — same bug class as #8, a different reserved namespace.

Fix

Added a suffix check: lower(d) NOT LIKE '%.arpa'.

10The screenshot field turned out to be free, high-value signal›
Not a bug — an opportunity found on review

A cross-check of every field dropped during ingestion found that Shodan pre-computes OCR text and scene labels on exposed RDP/VNC screenshots. No vision model needed — the analysis was already sitting in the record, unused.

Added

Wired screenshot.labels/screenshot.text into the schema and into scoring as top-priority evidence.

Result

Real examples now surface actual employee usernames OCR'd off exposed Windows RDP login screens — contact band grew from 202 to 242 accounts on this addition alone.

What generalized

Four lessons across twelve bugs

01

NULL is not false, three separate times

Issues #2, #5b, and #6 are the same root cause in three different parts of the pipeline. Any LIKE, SUM, or = touching a nullable column needs an explicit NULL-safety check by default now, not as an afterthought.

02

"Close enough" hides real bugs

Issue #5 was only caught by refusing to accept 186,435 vs. 187,007 as noise. A summary statistic is a claim to verify, not a number to glance at.

03

A denylist is a floor, not a ceiling

Every brand/placeholder/ISP fix (#7, #8, #9, #11) is the same shape: a keyword list will always miss cases outside what's been looked at so far. The fix is cheap, generalizable checks plus honestly documenting the residual noise.

04

Precision over recall, consistently

Every fix here trades some correctly-resolved companies for fewer incorrectly-resolved ones. That's a deliberate, stated architectural trade-off — not an accident of running out of time.
